## Introduction

A direct excerpt from the GitHub Discussion that preceded this proposal: [#5304]().

> This proposal [therefore] suggests a way forward on unlocking the means to describe security profiles in a suitably deterministic and loosely coupled way that provides API consumers with the affordances required to accurately understand the security requirements for a given Operation.

To add to this: The proposal also provide an approach to provide affordances for agentic use cases that enable AI agents to read and assemble OpenAPI-based tooling in a deterministic way.

## Motivation

This excerpt is again from the GitHub Discussion referenced [above](#introduction).

> The OpenAPI Specification provides a number of Security Scheme objects that are, largely speaking a "point in time" view of a security requirement.
>
> Take OAuth Flow Objects for example. OAuth Flow objects create a description of the security requirements for invoking given Operation that requires providing static properties that may not duplicate properties from the source of truth for the OAuth implementation. This duplication creates an inherent risk of drift, with security properties being updated in two places, with the OpenAPI view of OAuth often often much less rich than say - for example - OAuth Server Metadata.
>
> Security Scheme Objects therefore potentially create a tight coupling between a given Operation Object (or the entire API description) and a snapshot of the OAuth configuration for that Operation. This approach served older versions of the OpenAPI Specification adequately enough, but the evolution of the security space and the creation of profile-based OAuth and OpenID Connect specification, such as the [FAPI 2.0 Security Profile](https://openid.net/specs/fapi-security-profile-2_0-final.html), has resulted in a significant gap between what the OpenAPI Specification can describe, and what such security profiles need to describe to API consumers.

The analysis above describes the current "state of the union" in the OpenAPI Specification viz. how API security, especially complex profiles like the FAPI security profiles, are currently supported. Profile like FAPI cannot be described in a clear and authoritative manner, because OpenAPI lacks sufficient richness to describe them. However, "porting" all objects from a profile like FAPI to OpenAPI is almost certainly not the answer, because this creates a maintenance overhead for allowing OpenAPI to keep pace with changes to a security profile.

A middle ground is therefore required that allows the OpenAPI Specification to "carry" a suitably deterministic vocabulary that defines the objects that apply to a given API Operation whilst still allow flexibility and portability. Taking the example of the FAPI 2.0 profile mentioned above, API security actually breaks down into many complex relationships, as shown in the following (AI-generated) diagram:

![Overview of FAPI 2.0 Components - Generated by Claude](./fapi2_security_profile_normative_references.svg)

Clearly representing all the RFC and BCPs here in the OpenAPI Specification is going to be impossible to achieve _in full_, but the Specification should be able to do "just enough" to provide a view of the security requirements that can do the following provide enough information for a Client to bootstrap the security requirement, and then potentially source data through external references to generate an appropriate representation (to be expanded on below...)

There is also a need to not "throw the baby out with the bath water" in that create completely flexible specifications with few deterministic references does nothing to grow the OpenAPI "brain", in that features to come cannot leverage existing features. Going back to OAuth Flow Objects, these are actually a great feature to have, but leveraging them implies a fixed metadata footprint, in that `tokenUrl` **must** be supplied in all Flow objects and for example `authorizationUrl` must be declared for the `authorizationCode` Flow object. The shape of the object is therefore not manifestly incorrect, but the **_placement of the metadata is._**, especially in conjunction with security profiles like FAPI 2.0 where OAuth Server Metadata or OpenID Discovery are a very real and widely deployed part of the approach. "Security metadata" must therefore be abstracted away from the OpenAPI Specification itself, and encapsulated by appropriate rules to ensure values can be deterministically sourced.

We also have industry-specific needs that reflect how API security profiles are used in the real world. Going back to FAPI 2.0 again, while the FAPI Working Group maintains the core specification many jurisdictions define a local profile that tailors the constraints for the local market and sets out mandated or out of scope elements of the core specification, for example the [UAE Security Profile](https://openfinanceuae.atlassian.net/wiki/spaces/standardsv2dot1final/pages/702414912/Security+Profile+-+FAPI), which is then subject to certification. Being able to create a clear underlying definition of FAPI 2.0 in OpenAPI Specification **_and_** being able to inherit that profile for given market would be a massive boost for API consumers and providers alike.

The proposal herein therefore sets out the approach to achieving a revised Security Profile approach that achieve a number of goals reflecting the discussion above, namely:

- Allow complex security requirements to be modeled effectively, providing sufficient information to humans or machines to understand the construct or infer requirements in code from the security requirement.
- Allow API security requirements to be incorporated in the OpenAPI Specification in a modular way.
- Ensure that all security metadata is provided by means that reflect the salient approaches for discovery by clients.
- Allow security profiles to be reused by API providers, either directly or through industry standards bodies.

The approach to achieving these goals is described in the following sections.

## Proposed solution

One of the key goals above is to allow a security description to be developed in a modular way, with increasing levels of granularity and configurability. The basis of this approach is as follows:

1. A separate, dedicated OpenAPI Security Specification, referenced by the OpenAPI Specification is created to carry objects that are specifically for API security. The OpenAPI Security Specification will nominally be developed under the banner of a Standardized API Feature (SAF), but this is subject to discussion with TSC and more work on evolving the approach to ensure it is the right framework for delivery.
2. One-or-more features can be brought together to create a Security Profile, using the OpenAPI Security Specification as the main vocabulary but declaring them as a standalone specification. Examples of a Security Profile would be FAPI 1.0 Advanced, or FAPI 2.0.
3. A given Security Profile can also be tailored to fit customization frequently found in industry profiles, as discussed above, which is published in an Ecosystem Registry. Examples of a Registry entry would be the local FAPI security profiles found in open banking and open finance jurisdiction like Brazil, KSA, UAE, and UK.

The features of the approach all support creating an OpenAPI description document that declares _explicitly_ the security requirements for a given API Operation. In terms of "where stuff goes", the following describes the general (and non-exhaustive) approach.

| Item | Type | Maintained By |
| --- | --- | --- |
| RFC describing a security feature | OpenAPI Security Specification | Security SIG |
| Security feature with additional constraints on an RFC | Security Profile Framework | Security Profile |
| A constrained or tailored version of a Security Profile | Ecosystem Registry | Ecosystem Team |
| An API description that enforces security requirements for a given resource (that is describes) | OpenAPI Description Document | Standards Owner or API Provider |

The sections below expand on the approach and the shape of the proposed features.

### OpenAPI Security Specification

The first step defining a solution for Security Profiles is to create a separate OpenAPI Security Specification.

The rational for doing this is threefold:

1. The current OpenAPI Specification is already long and packed with information. Extending it for new, extensive subject matter is likely to make it even more dense.
2. API security constructs are dense in themselves. Adding a dense subject matter to an already dense OpenAPI Specification is likely to cause future pain as users and editors deal with the subject matter.
3. Modularity would allow security objects to evolve at their own pace, creating a useful loose coupling between aspects of the overall OpenAPI Specification.

Standardized security objects provides the means to describe objects that are a primitive of a given security schema, and are therefore open to a common solution. Fundamentally this does not differ to existing Security Scheme Objects, but the approach in the context of a SAF and the focus on runtime resolution means that

An example of this is a JSON Web Token (JWT). JWTs are protocol-bound through [JOSE](https://datatracker.ietf.org/wg/jose/about/) and [RFC 7519](https://datatracker.ietf.org/doc/html/rfc7519) and are limited in their implementation by characteristics such as the encoding method and "shape" of the object. Providing a defined object for JWTs will help ensure adherence to the underlying RFC whilst still providing information about the shape of the API.

A single standardized object avoids duplicating that structure across the various JWT uses, while still ensuring adherence to the underlying RFC. |

Without a dedicated object, there is no deterministic way to describe what an ID Token looks like for a given API, forcing clients to fall back on generic OIDC assumptions rather than what the API/profile actually issues. |

### Security Profile Framework

The Security Profile Framework is the means to describe a security profile or security feature in a way that does not automatically affect other parts of the OpenAPI Specification.

Taking a high-level example, the Security Profile for FAPI 2.0 would leverage the vocabulary of the OpenAPI Security Specification and then add addition constraints, for example:

- Specific ciphers prescribed by [RFC 9325](https://www.rfc-editor.org/info/rfc9325/#section-4.2) that are applied to a MTLS Object (incorporated in FAPI through BCP 195).
- Minimum TLS protocol version prescribed by [RFC 9325](https://www.rfc-editor.org/info/rfc9325/#section-4.1) that is applied to a MTLS Object (incorporated in FAPI through BCP 195).
- Certificate trust anchor and chain validation requirements prescribed by [RFC 5280](https://www.rfc-editor.org/info/rfc5280/) that are applied to a MTLS Object.
- Mandatory claims within a signed Request Object, prescribed by [RFC 9101](https://www.rfc-editor.org/info/rfc9101/) (JAR), that are applied to an OAuth Profile Object.

The Security Profile therefore provides an _extension point_ for the core OpenAPI Security Specification. The advantages of this approach are as follows:

- Nominally leverages the proposed introduction of the Standardized API Features (SAF) framework.
- Will allow a given Security Profile to move at its own pace, and solicit engagement from like-minded groups of experts.
- _Potentially_ allows for an alternative lexicon to be supported without tainting the core OpenAPI Specification or the baseline OpenAPI Security Specification.

### Ecosystem Registry

The Ecosystem Registry is the means to describe a locally tailored variant of a Security Profile, published and maintained by the standards body or ecosystem responsible for a given jurisdiction or industry vertical, rather than by the Security Profile's own working group.

Taking a high-level example, the FAPI 2.0 Security Profile is maintained centrally by the FAPI Working Group, but individual open banking and open finance jurisdictions — Brazil, KSA, UAE, and UK among them — layer their own constraints on top for local certification, such as the [UAE Security Profile](https://openfinanceuae.atlassian.net/wiki/spaces/standardsv2dot1final/pages/702414912/Security+Profile+-+FAPI). A Registry entry for a jurisdiction like this would typically:

- Mandate elements that the parent Security Profile leaves optional, for example requiring `certificateBoundAccessTokens` on the MTLS Object where FAPI 2.0 permits DPoP as an alternative sender-constraining mechanism.
- Mark elements of the parent Security Profile as out of scope for the local market, for example ruling out a Credential type that isn't recognized by the local Trust Framework.
- Substitute local references in place of generic ones, for example pointing the MTLS Object's trust anchor at a jurisdiction-specific root CA, or the Discovery Object at a local regulator's well-known endpoint.

The Ecosystem Registry therefore provides a second, narrower _extension point_, layered on top of a Security Profile in the same way a Security Profile is layered on top of the OpenAPI Security Specification. The advantages of this approach are as follows:

- Allows a single, canonical Security Profile (e.g. FAPI 2.0) to be maintained once by its working group, with jurisdictional variance kept out of the core definition.
- Allows ecosystems such as open banking and open finance bodies to publish and certify against their own tailored profile without forking or duplicating the underlying Security Profile.
- Keeps the certification boundary explicit: conformance to a Registry entry implies conformance to its parent Security Profile, plus whatever constraints are layered on top, mirroring the "Maintained By" separation set out in the [table above](#proposed-solution) (Security SIG → Security Profile → Ecosystem Team).

### Design View: OpenAPI Security Specification

#### Discovery Object

A Discovery Object provides scaffolding for client bootstrapping, where the client needs to retrieve security configuration at runtime.

For example, the following is an OIDC-compatible Discovery Object, with per-environment values.

```yaml
type: openIdConnect
endpoints:
  - type: Development
    url: https://example.com/discovery/dev/.well-known
  - type: Production
    url: https://example.com/discovery/prod/.well-known
```

There is an argument that a `metadataProperties` property could be added that describes the available properties, but there is no supported protocol or approach for specifying this, so OpenAPI would be providing something genuinely esoteric that may be difficult for tooling makers to adopt.

#### JSON Web Token Object

A JSON Web Token Object describes a JWT, covering both its encoding/structure and its claims, regardless of whether it is used as a Client Assertion, a DPoP proof, a signed request object, or an ID Token.

```yaml
ClientAssertionJwtProperties:
  header: "#/components/schemas/ClientAssertionHeaderProperties"
  payload: "#/components/schemas/ClientAssertionPayloadProperties"
```

Note here that there are no "special" indicators for a given signing algorithm or other cryptographic constraint. The idea is to define the shape of the JWT - so serialization and deserialization happen in an expected and structured way - put the supported _constraints_ on the JWT are applied **_by Discovery and by the Security Profile Framework_**.

This shape fit with the idea of making runtime decisions based on the shape of the object and metadata that informs the Client or agent about the shape. The JSON Web Token Object defines that shape - probably the most significant missing piece of the puzzle in the OpenAPI Specification - and then discovery addresses the processing options.

#### Credential Object

A Credential Object describes an artifact presented by the client to authenticate itself to the AS or resource server, independent of its encoding.

The example above describes a Client Assertion as described by RFC 7523, which is implemented in Pushed Authorization Request ([RFC 9126](https://www.rfc-editor.org/info/rfc9126/)) and used in FAPI 2.0.

For this example the proposed object shape as defined in an OAD is as follows.

```yaml
type: jwtBearer
jwt: "#/components/jsonWebTokens/ClientAssertionJwtProperties"
```

Where:

- `jwtBearer` indicates compliance with RFC 7523.
  - This indicates to the client that `client_assertion_type` is set to `urn%3Aietf%3Aparams%3Aoauth%3Aclient-assertion-type%3Ajwt-bearer` (URL encoded).
- `jwt` is a JSON Web Token Object, which encapsulates the required directives for creating and verifying the Client Assertion.

#### Structured Authorization Request Object

A Structured Authorization Request Object describes the parameters of an authorization request that relies on a structured payload.

```yaml
type: richAuthorizationRequest
authorizationDetails:
  - "#/components/schemas/AccountAccessConsent"
  - "#/components/schemas/PaymentInitiationConsent"
```

Where:

- `richAuthorizationRequest` indicates compliance with [RFC 9396](https://www.rfc-editor.org/info/rfc9396/) (Rich Authorization Requests), which is how FAPI 2.0 and GNAP-aligned profiles carry structured consent (e.g. account access, payment initiation) in an `authorization_details` parameter rather than plain OAuth `scope` strings.
- `authorizationDetails` references the schema(s) of the `type` values a client can expect to send/receive, reusing the existing OpenAPI Schema Object rather than inventing a parallel mechanism.

#### MTLS Object

An MTLS Object describes a Mutual TLS configuration, including trust anchor and certificate chain validation requirements, that can be applied to client authentication or sender-constrained access tokens.

```yaml
type: tlsClientAuth
trustAnchor: "#/components/schemas/OpenBankingRootCA"
certificateBoundAccessTokens: true
```

Where:

- `tlsClientAuth` indicates compliance with [RFC 8705](https://www.rfc-editor.org/info/rfc8705/) client authentication via a CA-issued certificate (as opposed to `selfSignedTlsClientAuth`, which validates the certificate itself rather than a trust anchor).
- `trustAnchor` points to a description of the CA/trust anchor a presented certificate must chain to, per [RFC 5280](https://www.rfc-editor.org/info/rfc5280/).
- `certificateBoundAccessTokens` indicates whether access tokens issued off the back of this authentication are also sender-constrained to the same certificate (RFC 8705 §3), reusing the object for both client authentication and token binding rather than defining them separately.
- As with the JSON Web Token Object, cipher suite and minimum TLS version are deliberately absent here — those are profile-level constraints applied via the Security Profile Framework, not part of the base shape.

#### Token Object

A Token Object describes a token issued to the client that is intended to be consumed for its context, rather than treated as an opaque bearer credential.

```yaml
type: idToken
jwt: "#/components/jsonWebTokens/IdTokenJwtProperties"
```

Where:

- `idToken` indicates compliance with the [OpenID Connect Core 1.0](https://openid.net/specs/openid-connect-core-1_0.html) ID Token.
- `jwt` is a JSON Web Token Object reference, in the same way the Credential Object references one for a Client Assertion — the Token Object adds no encoding of its own, it only scopes which JSON Web Token Object represents a context-carrying token as opposed to a credential.

### Design View: FAPI 2.0

Considering the following components of FAPI:

OAuth Flows and Flow Objects are replaced by the Discovery Object and OAuth Profile object.

A Discovery Object sets a universal point of reference for an OpenID Discovery or OAuth Server Metadata server. The Discovery makes no assertions about the shape other than to set a profile, which would nominally be [OIDC Discovery 1.0](https://openid.net/specs/openid-connect-discovery-1_0.html) or [OAuth Server Metadata (RFC 8414)](https://www.rfc-editor.org/info/rfc8414).

```yaml
components:
  security:
    OAuthWellKnown:
      type: oauthServerMetadata
      urls:
        - name: Development
          environment: dev
          url: https://example.com/dev/.well-known/oauth-authorization-server
        - name: Certification
          environment: cert
          url: https://example.com/cert/.well-known/oauth-authorization-server
        - name: Production
          environment: prod
          url: https://example.com/prod/.well-known/oauth-authorization-server
```

An OAuth Profile Object is then largely driven by discovery data, because there is no requirement to restate properties that are available from the Discovery Object. This is one aspect of where the SAF construct _may_ become important, because the expectation is that the resolution of this information happens at runtime. This adopts an existing behaviour - Discovery is loosely supported in the OpenAPI Specification right now - but the intention is make this more deterministic, with the Security Profile Framework making the declaration of security scope more deterministic.

```yaml
components:
  security:
    AuthCodeFlow:
      type: oauthAuthCodeFlow
      discovery: "#/components/security/OAuthWellKnown"
```

The `AuthCodeFlow` object here is of the type `oauthAuthCodeFlow`, which indicates an Authorization Code grant type that adheres to boilerplate OAuth 2.0 semantics. With limited other information (like for example `client_id` and `client_secret`) a client could be generated on based on this information alone.

However, a FAPI 2.0 compliant Authorization Code grant type has a number of constraints and requirements beyond boilerplate OAuth 2.0, such as:

- Requires a Pushed Authorization Request to stage an Authorization Request

PKCE is an OAuth-bound requirement, and therefore becomes part of the OAuth Profile. Building on the OAuth Profile Object above:

```yaml
components:
  security:
    AuthCodeFlow:
      type: oauthAuthCodeFlow
      profile: fapi20
      discovery: "#/components/security/OAuthWellKnown"
      pkce: true
      par: true
```

### Design View: GNAP

GNAP, the Grant Negotiation and Authorization Protocol, is defined in [RFC 9635](https://www.rfc-editor.org/info/rfc9635/). Unlike FAPI 2.0, GNAP is not a profile of OAuth 2.0 — RFC 9635 states explicitly that "GNAP is not an extension of OAuth 2.0 and is not intended to be directly compatible with OAuth 2.0." This has a direct consequence for this Design View: the FAPI 2.0 section above works almost entirely by _constraining_ existing vocabulary (the Discovery Object, an OAuth Profile Object) via the Security Profile Framework. GNAP has no Discovery Object, no OAuth Flow, and no Authorization Request underneath it to constrain — so, unlike FAPI 2.0, it cannot be expressed as a Security Profile alone.

Considering the following components of GNAP:

- A **Client Instance** identifies itself to the AS by presenting a key directly in the grant request, rather than a pre-registered `client_id`, and must prove possession of that key using a proofing mechanism — `httpsig` ([RFC 9421](https://www.rfc-editor.org/info/rfc9421/), HTTP Message Signatures), `mtls` ([RFC 8705](https://www.rfc-editor.org/info/rfc8705/)), `dpop`, or an attached/detached JWS. GNAP forbids presenting a symmetric key by value.
- A **grant request** is sent directly to the AS's grant endpoint (there is no separate Authorization Request/token exchange split as in OAuth) and progresses through explicit states — `processing`, `pending`, `approved`, `finalized` — rather than OAuth's single-shot redirect-and-exchange.
- Where the AS cannot finalize a grant immediately, it returns a **continuation** response: a bound continuation access token and URI the client uses to resume or poll the pending request.
- User involvement is negotiated via explicit **interaction start** (`redirect`, `app`, `user_code`, `user_code_uri`) and **interaction finish** (`redirect`, `push`) methods, declared by the client up front, rather than OAuth's implicit assumption of a browser redirect.
- **Access tokens** are bound to the client's key by default (GNAP's equivalent of sender-constraining is the baseline, not an opt-in extension as it is for OAuth/FAPI via mTLS or DPoP); a token may still be flagged `bearer` where binding isn't required. A single grant can also yield access to multiple resources via `resource_references`, rather than one token per Operation/scope.
- Resource Server integration (how an RS validates a GNAP-bound token) is described in a companion document, not yet published as an RFC (`draft-ietf-gnap-resource-servers`) — this is an external dependency the proposal cannot resolve.

#### What this means for the OpenAPI Security Specification

Because GNAP is itself a normative RFC describing a security feature — not a constraint on one — the table in [OpenAPI Security Specification](#openapi-security-specification) is the right home for its core vocabulary, consistent with how JSON Web Token and MTLS were added. Candidate new/extended objects:

- **Grant Request Object** (new) — describes the shape of a GNAP grant request: the client key reference, the `access_token` request(s), and the interaction methods offered. This is GNAP's equivalent of the Discovery Object + OAuth Profile Object pairing, but there is no discovery step to lean on, so it likely needs to declare the AS grant endpoint directly rather than resolving it at runtime.
- **Continuation Object** (new) — describes the continuation token/URI pattern used to resume a `pending` grant. No OAuth equivalent exists for this, since OAuth has no multi-turn negotiation state machine.
- **Interaction Object** (new) — describes the interaction start/finish method(s) a client supports. Structurally closer to a Security Scheme discriminator than a payload shape.
- **Credential Object** (extend) — add `httpsig`, `mtls`, and `dpop` as `type` values alongside the existing `jwtBearer`, backed by the JSON Web Token Object (for `dpop`/`jws`/`jwsd`) or the MTLS Object (for `mtls`) rather than new objects, per the Credential Object's existing rationale of separating "how the client authenticates" from "how the artifact is encoded".
- **HTTP Message Signature Object** (new, possible) — `httpsig` (RFC 9421) proofs are not JWTs and don't fit the JSON Web Token Object's JOSE-shaped model, so representing them may need a sibling object rather than a variant of an existing one — this needs further design work rather than being assumed away.
- **Discovery Object** (open question) — GNAP does not mandate an OIDC/RFC 8414-style metadata document the way OAuth/OIDC-based profiles do; the grant endpoint is simply known/configured. Whether the existing Discovery Object gains a minimal `type: gnapGrantEndpoint` variant, or whether GNAP bypasses Discovery entirely in favour of a URL directly on the Grant Request Object, is an open question rather than a given.

#### What this means for the Security Profile Framework

GNAP's own extensibility (multiple proofing mechanisms, multiple interaction methods, optional bearer tokens) means that, exactly as with OAuth and FAPI 2.0, a specific ecosystem building on GNAP will still need a Security Profile to be deployable and certifiable. None of this is needed to support GNAP itself — it only applies once a concrete GNAP-based profile exists:

- Restricting which proofing mechanism(s) are permitted (e.g. mandating `httpsig` only, or forbidding `bearer` tokens so all access tokens are key-bound).
- Restricting which interaction start/finish methods are permitted (e.g. mandating `redirect`/`redirect` only, ruling out `user_code` for machine-to-machine clients).
- Mandatory or forbidden fields within the Grant Request (e.g. requiring specific `resource_references`, or subject-identifier claims), in the same way FAPI 2.0 mandates claims within a signed Request Object via [RFC 9101](https://www.rfc-editor.org/info/rfc9101/) (JAR).
- Reusing, unchanged, the existing MTLS Object constraints (ciphers, TLS version, trust anchor) wherever `mtls` proofing is selected — this is a case where the Security Profile Framework work is already done, not new.

#### Challenging the initial expectation

The expectation that GNAP belongs in the OpenAPI Security Specification, not the Security Profile Framework, holds for GNAP's core vocabulary — the table's own rule ("RFC describing a security feature" → OpenAPI Security Specification, maintained by the Security SIG) applies to RFC 9635 exactly as it does to RFC 7519 (JWT) or RFC 8705 (MTLS). But that rule is being stretched further than it has been so far: JWT and MTLS are _primitives_ reused across profiles, whereas GNAP is a complete alternative to OAuth 2.0 as the grant protocol itself. Two things follow that complicate a clean "GNAP = OpenAPI Security Specification" answer:

1. GNAP has its own optionality (proofing method, interaction method, bearer-vs-bound) in the same way OAuth does — so, exactly as FAPI 2.0 constrains OAuth via the Security Profile Framework, any real deployment of GNAP will need an equivalent Security Profile layered on top of these new base objects. Supporting GNAP is therefore necessarily a two-part change, not a one-part change confined to the base spec.
2. Not everything GNAP needs is new: its proofing mechanisms should extend the existing Credential/JSON Web Token/MTLS objects rather than duplicate them, so the honest scope of "new" OpenAPI Security Specification surface is narrower than "GNAP support" might suggest — mainly the Grant Request, Continuation, and Interaction objects, plus the open question of an HTTP Message Signature object.
